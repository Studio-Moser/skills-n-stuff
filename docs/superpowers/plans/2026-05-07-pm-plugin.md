# PM Plugin + Product-Pulse Restructuring — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Create a `pm` plugin that owns the full project management lifecycle (ingest, triage, reconcile, sprint-dev), strip product-pulse down to pure intelligence gathering, absorb research-scout into product-pulse as deep-dive, and deprecate the standalone research-scout plugin.

**Architecture:** Two focused plugins sharing `pulse-config.yaml` for infrastructure. Product-pulse produces research reports. PM reads those reports, triages items, manages specs via superpowers brainstorming/writing-plans, tracks work via GitHub Issues (or local markdown), and executes sprints with sub-agents. Backend abstraction via `gh` CLI for GitHub, YAML files for local.

**Tech Stack:** Markdown skill files (SKILL.md), YAML config, `gh` CLI for GitHub Issues, `yq` for YAML parsing. No compiled code. Verification is operational (manual skill runs), not unit-tested.

**Spec:** [docs/superpowers/specs/2026-05-07-pm-plugin-design.md](../specs/2026-05-07-pm-plugin-design.md)

## Phase 2: PM Skills

Each PM skill follows the same structural pattern as product-pulse skills: YAML frontmatter with `name` and `description`, then markdown body with phases. Config discovery uses the same walk-up pattern from product-pulse v0.2.0 but reads both `pulse-config.yaml` (shared infrastructure) and `.pm/config.yml` (PM-specific).

**Shared config discovery block** — every PM skill starts with this Phase 0.0. Write it once here; each skill includes it:

```markdown
### 0.0 Discover Configuration

**Shared config (pulse-config.yaml):**

Walk up from cwd, checking each directory for `pulse-config.yaml` directly and in common research-dir subdirs (`research/`, `Research/`, `docs/research/`). The first match wins; that file's parent directory is the **research directory** (`{research_dir}`).

\```bash
config_path=""
research_dir=""
dir="$PWD"
while [ "$dir" != "/" ]; do
  for sub in "" "research/" "Research/" "docs/research/"; do
    candidate="$dir/${sub}pulse-config.yaml"
    if [ -f "$candidate" ]; then
      config_path="$candidate"
      research_dir="$(cd "$(dirname "$candidate")" && pwd)"
      break 2
    fi
  done
  dir="$(dirname "$dir")"
done

if [ -z "$config_path" ]; then
  echo "No pulse-config.yaml found. Run /product-pulse:setup or /pm:setup first." >&2
  exit 1
fi

primary_repo_root="$(cd "$research_dir" && git rev-parse --show-toplevel)"
default_branch="$(yq '.default_branch // "main"' "$config_path")"
project_id="$(yq '.project_id' "$config_path")"
memory_connector="$(yq '.memory.connector // "shelby"' "$config_path")"
\```

**PM config (.pm/config.yml):**

Look for `.pm/config.yml` in `{primary_repo_root}`. If missing, tell the user to run `/pm:setup`.

\```bash
pm_config="$primary_repo_root/.pm/config.yml"
if [ ! -f "$pm_config" ]; then
  echo "No .pm/config.yml found. Run /pm:setup first." >&2
  exit 1
fi

backend="$(yq '.backend // "github"' "$pm_config")"
\```
```

name: setup
description: >-

  .pm/

### Task 2.2: Write `/pm:ingest` SKILL.md

**Files:**
- Create: `plugins/pm/skills/ingest/SKILL.md`

- [ ] **Step 1: Write the skill**

Write `plugins/pm/skills/ingest/SKILL.md`.

**Frontmatter:**
```yaml
name: ingest
description: >-
  Read research reports from product-pulse (daily, weekly, deep-dive) and
  create needs-triage items in the configured issue tracker. Diffs against
  existing issues, current codebase, and out-of-scope rejections to avoid
  duplicates. Uses ingestion watermarks to process only new reports.
  Trigger: "ingest research", "process reports", "import findings",
  or /pm:ingest.
```

**Body structure — implement these phases:**

- **Phase 0: Discover config** — Same shared config discovery block. Load `research_dirs` from `.pm/config.yml`. Load ingestion watermarks from `.pm/state.yml`.

- **Phase 0.1: Pull latest** — Iterate repos from pulse-config.yaml, pull default branch for each.

- **Phase 1: Scan for new reports** — For each directory in `research_dirs`, find report files newer than the watermark:
  ```bash
  find "$research_dir" -name "*-daily-research.md" -newer ".pm/state.yml" 2>/dev/null
  find "$research_dir" -name "*-strategy-brief.md" -newer ".pm/state.yml" 2>/dev/null
  find "$research_dir" -name "*-recommendations.md" -newer ".pm/state.yml" 2>/dev/null
  find "$research_dir/deep-dives" -name "*.md" -newer ".pm/state.yml" 2>/dev/null
  ```
  If no new reports, print "No new reports since last ingestion" and exit.

- **Phase 2: Extract action items** — For each report, dispatch a subagent (ingestion-analyst) to read it and extract:
  - Action items from the Action Items table (daily reports, deep-dives)
  - Recommendations from the "Suggested for Speccing" table (weekly recommendations)
  - Monitor alerts from weekly briefs
  Each extracted item has: title, description, source report, source section, suggested size, suggested priority, confidence rating.

- **Phase 3: Dedup and filter** — For each extracted item:
  - Check against existing open issues (GitHub: `gh issue list --label needs-triage,ready-for-agent --json title,body`, local: scan `.pm/items/`). Skip if title or description matches > 80%.
  - Check against `.pm/out-of-scope/` directory — read each rejection file, skip if the item matches a rejected concept.
  - Check against current codebase — for items that suggest implementing something, search the codebase to see if it's already done. Use `grep -r` across configured repos. Skip if already implemented.

- **Phase 4: Create items** — For each surviving item:
  - GitHub backend: `gh issue create --title "{title}" --body "{body}" --label "needs-triage,size/{size}"`. Include source attribution in the body.
  - Local backend: write YAML file to `.pm/items/{number}-{slug}.yml` with fields: title, body, labels, source, created_at.
  - Tag with suggested target repo if determinable from the report context.

- **Phase 5: Update watermarks** — Write updated timestamps to `.pm/state.yml`.

- **Phase 6: Summary** — Report: X reports scanned, Y items extracted, Z duplicates skipped, W out-of-scope skipped, V already implemented, U new items created.

Check: watermark logic, dedup against issues and out-of-scope, GitHub and local backend paths both covered, no hardcoded paths.

```markdown
# Ingestion Analyst

You are an action-item extraction agent. You receive a research report and extract all actionable items from it.

## Input

You receive:
- The full text of a research report
- The report type (daily-research, weekly-recommendations, deep-dive)
- The product context (condensed)

## Output

Return a structured list of extracted items. For each item:

- **title**: Short, specific action (imperative voice, under 80 chars)
- **description**: 2-3 sentences of context from the report
- **source_report**: filename of the source report
- **source_section**: which section of the report this came from
- **suggested_size**: S, M, L, or XL based on the report's effort rating
- **suggested_priority**: P0-P3 based on the report's impact rating
- **confidence**: High, Medium, or Low (from the report's confidence rating)
- **target_repo**: which repo this work should happen in (if determinable, else "unknown")

## Rules

- Extract from **Action Items** tables in daily and deep-dive reports
- Extract from **Suggested for Speccing** tables in weekly recommendations
- Extract from **Monitor Alerts** in weekly briefs (these become monitor-type items)
- Do NOT fabricate items not present in the report
- Do NOT combine multiple items into one — keep them granular
- Do NOT editorialize — use the report's own language and assessments
- If an item references a specific URL or tool, include it in the description
```

### Task 2.4: Write `/pm:triage` SKILL.md

**Files:**
- Create: `plugins/pm/skills/triage/SKILL.md`

- [ ] **Step 1: Write the skill**

Write `plugins/pm/skills/triage/SKILL.md`.

**Frontmatter:**
```yaml
name: triage
description: >-
  Process needs-triage items through the full pipeline: sort (reject/dedup),
  spec (brainstorming + writing-plans for M/L/XL items), score against the
  agent-ready checklist, and promote to ready-for-agent or reject to
  out-of-scope. Interactive — you confirm every decision.
  Trigger: "triage", "process backlog", "review incoming items", "spec items",
  or /pm:triage.
```

**Body structure — implement these phases:**

- **Phase 0: Discover config and load items** — Shared config discovery. Pull all `needs-triage` items:
  - GitHub: `gh issue list --label "needs-triage" --json number,title,body,labels,assignees --limit 100`
  - Local: scan `.pm/items/` for files with `labels: [needs-triage]`
  Read CONTEXT.md for domain terms. Read `.pm/out-of-scope/` directory listing.

- **Phase 1: Sort** — Present each item to the user with a recommendation:
  - **Reject** — clearly out of scope or previously rejected concept. Create `.pm/out-of-scope/{slug}.md` from template. Close the issue/item.
  - **Duplicate** — matches an existing open item. Link to the duplicate, close.
  - **Keep** — proceed to Phase 2.
  For each item, show: title, description, source, suggested size. Ask user to confirm recommendation.

- **Phase 2: Spec** — For items that survived Phase 1:
  - **S-sized items** with clear descriptions: skip speccing, go directly to Phase 3.
  - **M/L/XL items**: invoke the spec creation flow:
    1. Call `Skill({ skill: "superpowers:brainstorming" })` with the item as the problem statement. Read CONTEXT.md and out-of-scope to inform the brainstorm.
    2. After brainstorming produces a design, call `Skill({ skill: "superpowers:writing-plans" })` to write the implementation spec.
    3. For GitHub backend: update the issue body with the spec content (structured headers: Goal, Context, Code References, Approach, Chunks, Acceptance Criteria).
    4. For local backend: write spec to `planning/specs/{number}-{slug}.md`.
  - This phase is the most time-intensive. Process one item at a time. After each spec, ask the user if they want to continue with the next item or stop.

- **Phase 3: Score** — Evaluate each specced item against the agent-ready scorecard:
  ```
  Agent-Ready Scorecard:
  1. [ ] Clear description (what, not how)
  2. [ ] Explicit acceptance criteria
  3. [ ] Linked code references with target repo
  4. [ ] Negative constraints (cross-refs .pm/out-of-scope/)
  5. [ ] Bounded scope (single deliverable, one repo)
  6. [ ] No open design questions
  ```
  Present the scorecard result. Items passing all 6 → recommend `ready-for-agent`. Items failing → show which criteria failed, ask user:
  - Fix it now (edit the spec inline)
  - Mark as `ready-for-human` (needs human attention on the failing criteria)
  - Leave as `needs-info` (stays in triage for later)

- **Phase 4: Promote** — For items the user approves:
  - GitHub: remove `needs-triage` label, add `ready-for-agent` (or `ready-for-human`). Add size label, target repo label, priority label.
  - Local: update YAML file labels.
  - If a parent epic exists, add as sub-issue: `gh api graphql` to create sub-issue relationship.
  - Update `planning/todos.md` if maintaining the markdown backlog: add a row to the appropriate sprint section in Ready.

- **Phase 5: Summary** — X items triaged, Y rejected, Z specced, W promoted to ready, V need human attention.

Check: superpowers skill invocations use correct syntax, scorecard has all 6 criteria from spec, out-of-scope template matches `templates/out-of-scope-entry.md`, both backends covered.

### Task 2.5: Write scorecard-evaluator agent

- [ ] **Step 1: Write the agent**

Write `plugins/pm/agents/scorecard-evaluator.md`:

```markdown
# Scorecard Evaluator

You evaluate whether a work item is ready for an AI agent to implement. You apply a strict 6-point checklist and report which criteria pass or fail.

## Input

You receive:
- The item's title, description, and spec (if any)
- The project's CONTEXT.md (domain terminology)
- The project's .pm/out-of-scope/ directory listing (rejection KB)
- The list of configured repos

## Evaluation Checklist

Score each criterion as PASS or FAIL with a one-line explanation:

1. **Clear description** — Does the item describe WHAT to build, not HOW? A good description states the desired outcome. A bad one prescribes implementation details without explaining the goal.

2. **Explicit acceptance criteria** — Are there specific, testable conditions that define "done"? Vague criteria like "works well" or "is performant" fail this check.

3. **Linked code references** — Does the spec reference specific files, modules, or APIs in the target repo? An agent needs to know WHERE to start. References should include the target repo name for multi-repo projects.

4. **Negative constraints** — Does the spec say what NOT to do? Check against .pm/out-of-scope/ for related rejections. If a rejection exists for a related concept, the spec should reference it. Missing negative constraints = FAIL only if related out-of-scope entries exist.

5. **Bounded scope** — Is this a single deliverable in one repo? Items that span multiple repos or require multiple independent changes should be split. "Add feature X AND refactor Y" is unbounded.

6. **No open design questions** — Are there unresolved questions in the spec? Look for "TBD", "TODO", question marks in headers, or explicit "Open Questions" sections with unanswered items.

## Output

Return:
- **Score**: X/6
- **Verdict**: ready-for-agent (6/6), ready-for-human (4-5/6 with only minor gaps), needs-info (< 4/6)
- **Per-criterion results**: PASS/FAIL with explanation for each
- **Suggested fixes**: For each FAIL, what specifically needs to be added or changed
```

Write `plugins/pm/skills/reconcile/SKILL.md`.

**Frontmatter:**
```yaml
name: reconcile
description: >-
  Sync project reality with the issue tracker. Scans git history for completed
  items, detects stale work, classifies deferred blockers, updates epic
  progress, proposes CONTEXT.md updates and ADRs. Run after sprints, after
  merges, or periodically.
  Trigger: "reconcile", "sync issues", "clean up backlog", "check progress",
  or /pm:reconcile.
```

**Body structure — implement these phases:**

- **Phase 0: Discover config** — Shared config discovery. Load all repos from pulse-config.yaml.

- **Phase 1: Completion tracking** — For each configured repo:
  ```bash
  git log --since="$(yq '.last_reconcile // "2 weeks ago"' .pm/state.yml)" --oneline --all | grep -oE '#[0-9]+'
  ```
  For each referenced issue number:
  - GitHub: `gh issue view {number} --json state,title,labels`
  - If the issue is still open and the referencing commit is on the default branch → mark as done (or prompt user for confirmation)
  - Check PRs: `gh pr list --search "{number}" --state merged --json number,title`
