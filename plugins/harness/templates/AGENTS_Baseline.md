**House rules apply to all changes in this repo.** Full text: https://raw.githubusercontent.com/Studio-Moser/skills-n-stuff/main/plugins/harness/references/house-rules.md . In short: never commit to `main` (branch `{type}/{desc}`); Conventional Commits; PRs use What/Why/Testing; shortest diff / reuse first / root cause; size the ceremony to the change class (repo changes only — Polish / Small / Feature, name it first; polish runs its gates at the checkpoint, not per edit; non-code asks get no engineering workflow); show pasted test output; no secrets in the diff.

**Delegate through the Harness contract.** Consumers construct a Harness Request and select only a semantic route. Harness resolves the model and executor, propagates authority and constraints without widening them, and dispatches the bounded work. Workers return evidence in a Harness Result; parent agents reproduce the named proof before accepting the outcome. If Harness is not configured, run `/harness:setup`; project instructions never embed personal route values or provider mechanics.

**Explicit Harness tasks load their skill first.** When a task directly supplies a Harness Request or requires a Harness Result, invoke the matching namespaced Harness skill before acting; operation `execute`, route resolution, and typed pre-dispatch blockers use `/harness:execute`.

**Take your own worktree for parallel work** — `git worktree add ../{repo}-{task} -b {type}/{desc} origin/main`. Several sessions often share one checkout, and a checkout has one HEAD and one index: another session switching branches between your commands re-parents your work onto theirs. In a shared checkout, verify HEAD in the *same* command that creates the branch, stage explicit paths instead of `git add -A`, and check `git log --oneline origin/main..HEAD` before pushing.

**Questions are read-only.** When asked about the code — how something works, why it behaves that way, whether an approach is sound — answer it. Don't start editing until the ask is to change something.
