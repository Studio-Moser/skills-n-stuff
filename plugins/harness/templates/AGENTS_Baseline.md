**House rules apply to all changes in this repo.** Use this self-contained summary for ordinary work; load deeper workflow references only when an active workflow requires a named detail: never commit to `main` (branch `{type}/{desc}`); Conventional Commits; PRs use What/Why/Testing; shortest diff / reuse first / root cause; size the ceremony to the change class (repo changes only — Polish / Small / Feature, name it first; polish runs its gates at the checkpoint, not per edit; non-code asks get no engineering workflow); show pasted test output; no secrets in the diff.

**Route only explicit Harness delegation through the Harness contract.** Do repository work directly unless the user or an active workflow explicitly requests Harness delegation. For delegated work, consumers construct a Harness Request and select only a semantic route. Harness resolves the model and executor, propagates authority and constraints without widening them, and dispatches the bounded work. Workers return evidence in a Harness Result; parent agents reproduce the named proof before accepting the outcome. If a delegated request cannot be routed because Harness is not configured, run `/harness:setup`; do not run setup merely because an ordinary repository task lacks routing. Project instructions never embed personal route values or provider mechanics.

**Take your own worktree for parallel work** — `git worktree add ../{repo}-{task} -b {type}/{desc} origin/main`. Several sessions often share one checkout, and a checkout has one HEAD and one index: another session switching branches between your commands re-parents your work onto theirs. In a shared checkout, verify HEAD in the *same* command that creates the branch, stage explicit paths instead of `git add -A`, and check `git log --oneline origin/main..HEAD` before pushing.

**Questions are read-only.** When asked about the code — how something works, why it behaves that way, whether an approach is sound — answer it. Don't start editing until the ask is to change something.
